# Specs transcribed from a maker's datasheets

`datasheets/<maker>/` holds module specs read from a manufacturer's own datasheets, for makers that publish datasheets
but no PVsyst files. Unlike `examples/` (fictional) and `library/` (generated from the CEC lists), these are real
products under their real names, and every figure in them is one the datasheet prints. The first, and so far only,
maker is Waaree (`datasheets/waaree/`, 159 specs from 22 datasheets, 2026-10-13). Their PAN files are in SolarLayout
Rooftop's module library.

## What a maker's folder holds

| File | What it is |
|---|---|
| `README.md` | The maker's series and counts, what came from the datasheets, every assumption, what was left out and why, how well the specs fit, and the commands that rebuild them |
| `sources.csv` | One row per datasheet used: `pdf`, `series`, `technology`, `document` (the maker's document number, as printed on the sheet), `url` |
| `make_specs.py` | Reads the datasheets' text (`pdftotext -layout`) and writes one spec per power bin into `specs/` |
| `specs/*.yaml` | The specs, named `<Maker>_<Model>.yaml`. Generated by `make_specs.py`; never edited by hand |

The PDFs are the maker's documents and are not committed: `sources.csv` says where each one is.

## Rules

1. **Only what the sheet prints.** STC values per bin, the three temperature coefficients, the low-light figure
   (`low_light_rel_eff_pct`), maximum system voltage, size, weight, cell count and layout, bifaciality, bypass diodes.
   Never a figure from another source dressed as the datasheet's.
2. **Every gap is said.** A figure the sheet does not give, and is assumed, gets a line in the spec's
   `provenance_notes`: what was taken, and why (for example, the series' other sheets state it). It ends up in the PAN
   file's Remarks. The maker's README lists the same assumptions.
3. **One datasheet, one document number.** `data_source` is `<Maker> datasheet <document>`. `make_specs.py` refuses a
   text whose document number differs from `sources.csv`, so a new revision is a deliberate change to `sources.csv`,
   never a silent one. When a revision replaces another with the same figures, keep the newer one and say so in the
   README.
4. **Strict fits only.** Every spec must fit without warnings (`ds2panond module <spec> --strict`). A spec that warns is
   a transcription error to fix, or a datasheet to leave out (listed in the README with the reason).
5. **The specs are output.** To change one, change `make_specs.py` or `sources.csv` and run it again; then check that
   the specs you did not mean to change did not move (`git diff datasheets/<maker>/specs`).

## Adding a maker

1. Find the maker's datasheets (download center) and choose the current framed modules. Leave out a superseded revision
   and products the datasheet does not describe fully (no temperature coefficients in the text, for example).
2. Download the PDFs into a folder **outside** the repository, and extract their text:
   `pdftotext -layout <pdf> <txt>` (poppler).
3. Copy `datasheets/waaree/` as a starting point and adapt `make_specs.py` to the maker's table layout: the model
   pattern, the column order of the electrical table, the labels of the coefficients and the size. Keep it typed and
   ruff-clean; it is checked with the rest of the repository.
4. Write `sources.csv`, run `make_specs.py`, and read a sample of specs against their PDFs, row by row, before trusting
   the parser: the first, the last and one in the middle of each sheet, and every figure the README calls assumed.
5. Build the PAN files with `--strict` into `out/` and compare the fit with the datasheet (`ds2panond` prints the
   targets against the model).
6. Write the maker's README from Waaree's. `tests/test_datasheets.py` picks the new folder up by itself: it checks that
   every spec is valid and names a datasheet in `sources.csv`, and fits the highest bin of each datasheet. Fitting
   every spec would take most of a minute; the full `--strict` build is part of step 5.
7. Add a line to `CHANGELOG.md` under Unreleased.

## Using the files in SolarLayout Rooftop

The app's module library may hold files fitted from a maker's datasheet where the maker publishes no PAN file (its
decision D115). Its `docs/equipment-library.md` says how they are added: copied in as `<Maker>_<Model>.PAN`, read by the
engine's own readers, the maker named as people know it. Before they go in, each file is read by the app's catalog
reader and its one-diode model, which must give the nameplate at STC within 0.5 % and the datasheet's low-light figure.
